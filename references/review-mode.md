# 제안 승인형 윤문

작가가 수정안을 하나씩 보고 고른 뒤에만 원고에 반영하는 방식이다. 윤문 결과를 한 번에 내는 기본 경로와 달리, 원고가 작가에게 중요하고 고친 이유를 작가가 직접 판단해야 할 때 쓴다. 공유받은 원고 수정 스킬(edit-desk)의 절차 구조를 참고해 새로 썼다. 문체 기준과 금지어 목록은 가져오지 않았다. 이 스킬의 철칙, 보존 잠금, 게이트가 그대로 우선한다.

## 1. 언제 쓰나

- 작가가 "제안만 먼저 보여줘", "내가 골라서 반영할게"라고 할 때
- 칼럼·에세이처럼 문장이 작가의 이름으로 나가는 글
- 수정 항목이 많아 어떤 수정이 어디에 닿는지 추적해야 할 때

단순 맞춤법 정리나 이미 승인된 문장 치환에는 쓰지 않는다. 그때는 기본 윤문 경로로 충분하다.

## 2. 시작 전에 잠글 것

1. **기준본:** 이번 판의 원고 파일을 하나로 정한다. 수정은 항상 이 파일의 복사본에 한다. 원본은 덮어쓰지 않는다.
2. **중심 판단 문장:** 글이 말하려는 판단을 원문 근거만으로 한 문장에 쓴다. 한 문장으로 줄지 않으면 억지로 합치지 않고 이유를 적는다.
3. **지킬 문장:** 작가가 "이건 건드리지 마"라고 한 문장과 제목 범위 판정을 적는다. 제목이 범위에 들면 제목도 수정 후보다. 아니면 제목은 그대로 둔다.
4. **보존 잠금:** 숫자, 고유명사, 직접 인용, 출처는 기본 잠금이다. 잠금 구간은 수정안에 올리지 않는다.

## 3. 제안: 수정 번호 표

`review-signals`로 기계 신호를 먼저 본다. 신호는 편집 후보이며 결함 판정이 아니다. 양·빈도 단정(SIG-1), 1인칭 글의 저자 3인칭 표기(SIG-2), 같은 시작말 반복(SIG-3), 문단 안 종결 혼용(SIG-4)을 본다. 어체(「~했어」「~더라고」)도 종결로 읽으므로 스레드 글의 말투 혼용도 잡는다.

```text
python scripts/korean_writing.py review-signals 원고.md [--json]
```

일반 진단(`diagnose`)과 신호를 합쳐 사람이 읽고 수정안을 쓴다. 수정안마다 아래 칸을 채운다.

| 칸 | 쓰는 법 |
|---|---|
| 수정 번호 | E1, E2처럼 이어서 붙인다. 이후 모든 단계가 이 번호로 부른다 |
| 왜 | 독자가 어디서 걸리는지로 쓴다. "규칙 위반"이 아니라 "숫자가 없어 독자가 믿을 근거가 없다"처럼 쓴다 |
| 수정 전 | 원고에서 그대로 복사한다. 한 글자도 바꾸지 않는다 |
| 수정 후 | 바꿀 문장 전문. 요약이나 "이런 식으로"가 아니다 |
| 추천 | 반영 / 보류 / 유지 중 하나와 한 줄 이유 |

수정 후 문단은 작가가 실제로 보게 될 글이다. 승인은 이 문장에 대한 승인이다.

## 4. 저자 확인 물음

수정을 확정하려면 작가만 아는 사실이 필요할 때가 있다. 물음을 둘로 나눈다.

- **필수:** 답에 따라 원고에 남는 문장이 달라진다. 반영한 문장이 저자의 경험을 말하거나, 확인 대기 수치가 원고에 남을 때다.
- **선택:** 답하면 보강할 수 있지만 지금 원고는 성립한다. 가정형 문장이거나 원고 사실을 새로 만들지 않을 때다.

필수·선택은 제안 단계에서 정하고 이후에 조용히 바꾸지 않는다. 바꾸려면 이유를 한 줄로 적는다. 작가가 답하지 않은 사실은 만들지 않는다. 경험, 수치, 인용이 필요하면 `확인 필요`로 남긴다.

## 5. 반영: 승인 문장 치환

작가가 고른 항목만 남긴 치환 목록을 만든다.

```json
[{"id": "E1", "old": "수정 전 문장", "new": "수정 후 문장"}]
```

```text
python scripts/korean_writing.py apply-edits 치환.json 원고.md 반영본.md [--allow-locked] [--overwrite] [--json]
```

- 수정 전 문장이 원고에 정확히 1회 나올 때만 치환한다. 0회나 2회 이상이면 파일을 쓰지 않는다. 위치를 더 길게 잡아 다시 시도한다.
- 바꿀 구간이 겹치면 쓰지 않는다. 겹친 쌍은 하나로 합친다.
- 인용·코드 구간과 겹치면 쓰지 않는다. 작가가 인용 수정을 직접 지시한 때만 `--allow-locked`를 쓴다.
- 원본과 같은 경로, 이미 있는 출력 파일은 거절한다.
- `--check`를 붙이면 치환 뒤 `preserve`와 `verify_gates`를 바로 이어서 돌린다. 숫자·인용 손실이나 게이트 중단이면 종료 코드 1이므로 6절의 수동 확인을 따로 하지 않아도 된다. 게이트가 통과해도 의미 확인은 사람이 한다.
- 결과에 분량 비율, 숫자 변화, 90자 이상 새 문장이 나온다. 분량이 120%를 넘으면 반영 전에 작가에게 먼저 묻는다.

작가가 승인하면서 문장 수정을 지시했거나 저자 답변으로 새 문장을 써야 하거나 문단 순서를 옮기기로 한 경우에는 치환이 아니라 해당 항목만 다시 쓴다. 이때도 승인되지 않은 항목은 건드리지 않는다.

## 6. 반영 후 확인

1. `apply-edits`의 숫자 변화를 승인 항목과 짝짓는다. 짝이 없는 변화는 사실 훼손이므로 되돌린다.
2. `preserve 원고.md 반영본.md`와 `verify_gates.py`를 돌린다.
3. 항목마다 판정한다.

```text
E1  해결          — 확인한 근거 한 줄
E2  부분 해결     — 남은 부분
E3  보류          — 작가 선택
E4  새 문제       — 위치. 지금 고치지 않고 다음 판 후보로만 적는다
```

새 문제에는 이어지는 번호를 바로 붙인다. 해결된 문제를 다른 말로 다시 제기하지 않는다.

## 7. 게시 판정

| 판정 | 조건 |
|---|---|
| 게시 가능 | 승인 항목 전부 해결, 필수 저자 확인 0건, 확인 필요 사실 0건 |
| 게시 보류 | 필수 저자 확인 또는 확인 필요 사실이 남음 |
| 재편집 필요 | 새 문제가 중심 판단을 흔들거나 보존 게이트가 막음 |

선택 물음은 판정에 세지 않는다. 작가가 `유지`로 고른 구간에 남은 문제는 고치지 않고 "유지 구간 잔여: 위치 — 항목"으로만 보고한다.

## 8. 교정 기록과 규칙

작업 도중에 규칙을 바꾸지 않는다. 작가가 고친 방향이 규칙과 어긋나면 교정 카드(상황, 제안, 작가의 선택, 이유)로 적어 둔다. 같은 종류가 세 번 반복되면 규칙 후보로 올린다. 거절 사유는 원문 그대로 남긴다.

실제 원고 5편이 쌓이기 전에는 채택률이나 거절 사유 통계로 규칙을 고치지 않는다. 표본이 적으면 우연과 구분되지 않는다. 살필 지표는 채택률, 거절 사유 반복, 반영 뒤 작가가 다시 고친 곳, 판정이 맞았는지다.

## 9. 한계

- `review-signals`는 휴리스틱이다. 어체 판별은 종결 어미 모양만 보므로(`channel-check` CH-15와 `voice-profile`도 같은 판별을 쓴다) 명사 끝의 「야」「아」「지」를 어체로 잘못 읽을 수 있다.
- SIG-2는 글이 「사용자」를 UX 대상으로 다룰 때도 잡힌다. 글의 대상이면 그대로 둔다.
- `apply-edits`의 통과는 문장이 정확히 치환됐다는 뜻이다. 의미가 보존됐다는 증명이 아니다. 부정, 가능성, 인과, 주체는 사람이 읽어 확인한다.
- 이 절차의 효과는 검증하지 않았다. 테스트는 명령의 동작을 확인하며 글 품질 평가가 아니다.
- 검증용 결함 심은 원고는 실제 원고와 분리해 두고, 시험 원고의 문장을 예시에 옮기지 않는다.
