# 블로그 글쓰기

블로그 글은 검색으로 들어온 사람이 질문의 답을 얻고 나가는 글이다. 이 문서는 두 환경을 다룬다.

| 환경 | 채널 값 | 서식 | 발행물 |
|---|---|---|---|
| 네이버 블로그 | `naver-blog` | 평문으로 납품. 굵게·색은 사용자가 에디터에서 넣는다 | 제목, 본문, 사진 자리, 태그 |
| 자체 블로그·워드프레스·티스토리 | `blog` | Markdown 소제목·목록·링크 | 제목, 본문, 메타 설명, 주소 슬러그, 카테고리·태그, 내부 링크 |

형식 수치는 `../scripts/channel_specs.json`이 원천이며 대부분 운영 가정값이다. 검색 노출 순위가 정해지는 방식은 확인할 수 없는 영역이다. 이 문서의 기준은 "독자의 질문에 답하는 글"을 만드는 편집 기준이고 노출을 보증하지 않는다.

## Step 1. 검색 의도 정하기

한 글은 질문 하나에 답한다.

확인할 것:

- 독자의 질문. 검색창에 칠 만한 문장으로 적는다
- 핵심어 1개와 보조어 2~3개. 사용자가 정한다
- 글 종류: 방법·순서 / 비교·선택 / 후기·체험 / 개념 해설 / 사례 분석
- 필자의 재료: 직접 한 일, 찍은 사진, 가진 수치, 받은 질문
- 연결할 글: 같은 블로그의 관련 글, 시리즈의 앞뒤 글

핵심어 후보를 요청받으면 주제에서 나올 만한 표현을 제안할 수 있다. 검색량·경쟁 강도·순위는 도구로 조회한 값이 없으면 말하지 않는다. 사용자가 조회한 값을 주면 그 값을 출처·기준일과 함께 쓴다.

같은 질문에 답하는 글이 블로그에 이미 있으면 새 글보다 기존 글 보강이 나은지 사용자에게 묻는다.

## Step 2. 구조

| 글 종류 | 구조 |
|---|---|
| 방법·순서 | 무엇이 되는지와 조건 → 준비물 → 단계 → 자주 막히는 곳 → 정리 |
| 비교·선택 | 누구에게 필요한 비교인지 → 선택 기준 → 항목별 비교 → 상황별 권고 |
| 후기·체험 | 이용 조건(일시·비용·제공 여부) → 겪은 순서 → 좋았던 점과 아쉬운 점 → 맞는 사람 |
| 개념 해설 | 질문 → 한 문단 답 → 풀어 쓴 설명 → 예 → 헷갈리기 쉬운 것 |
| 사례 분석 | 사례의 상황 → 한 일 → 결과 → 다른 곳에 적용할 때의 조건 |

소제목:

- 소제목만 읽어도 글의 순서가 보여야 한다.
- 소제목은 그 절의 내용을 말한다. "첫 번째 방법"보다 "사진부터 다시 찍는다"가 낫다.
- 핵심어는 뜻이 통하는 소제목에만 넣는다.
- 자체 블로그는 1,500자 이상이면 `##` 2~6개(가정값). 짧은 글에 소제목을 여럿 넣지 않는다.
- 네이버 블로그는 소제목을 한 줄 단독 문단으로 쓰고 꾸밈은 사용자가 에디터에서 한다.

제목:

- 본문이 실제로 주는 것을 말한다.
- 핵심어를 앞쪽에 둔다.
- 네이버 15~35자, 자체 블로그 50자 이내(가정값).
- 숫자를 쓰면 본문 항목 수와 맞춘다. 연도를 쓰면 내용이 그 연도 기준인지 확인한다.
- 후보는 형태를 달리해 3~5개: 방법형, 대상+조건형, 비교형, 질문형, 판단형.

## Step 3. 초안

도입:

- 첫 문단에서 이 글이 어떤 질문에 답하는지와 답의 범위를 밝힌다.
- 답이 짧으면 첫 문단에 답부터 쓴다. 자세한 설명은 뒤에 둔다.
- 핵심어는 첫 문단에 한 번, 문맥에 맞게.
- 인사말과 "오늘은 ~에 대해 알아보겠습니다"는 줄인다. 블로그의 고정 인사가 있으면 사용자 방식대로 둔다.

본문:

- 한 문단에 한 가지. 네이버는 150자 이내, 자체 블로그는 400자 이내(가정값).
- 순서는 번호로, 비교는 표로. 네이버 평문에서는 표 대신 항목별 문단으로 쓴다.
- 수치·가격·영업시간·제도는 기준일을 적는다. 확인하지 못한 값은 `[확인 필요]`.
- 핵심어를 채우려고 문장을 늘리지 않는다. 같은 말이 반복되면 대명사나 다른 표현으로 바꾼다.
- 직접 해 본 내용과 조사한 내용을 구분해 쓴다. 해 보지 않은 것을 후기처럼 쓰지 않는다.
- 사진 자리는 `[이미지: 무엇을 보여 주는 사진인지]`로 표시한다. 사용자가 가진 사진만 계획에 넣는다.

링크(자체 블로그):

- 관련 글은 본문에서 그 내용이 필요한 자리에 건다.
- 링크 문구는 대상의 제목이나 이름으로 쓴다. "여기", "이 글"은 `channel-check`가 CH-13으로 올린다.
- 있는지 확인하지 못한 글의 주소를 만들지 않는다. `[링크: 글 제목 — 주소 확인 필요]`로 둔다.

결론:

- 질문에 대한 답을 두세 문장으로 다시 준다.
- 다음에 읽을 글이나 할 일이 있으면 하나만 안내한다.

광고·협찬·제공을 받은 글은 그 사실을 글 앞쪽에 밝힌다. 표시 문구와 위치는 사용자가 따르는 기준에 맞춘다.

## Step 4. 점검

1. 제목이 약속한 것을 본문이 주는가
2. 첫 문단만 읽어도 무슨 질문의 답인지 아는가
3. 소제목만 훑어도 순서가 보이는가
4. 문단마다 새 정보가 있는가. 분량을 채우는 문단이 없는가
5. 수치·날짜·가격·이름이 자료와 같고 기준일이 있는가
6. 핵심어가 문맥 없이 반복되는 곳이 없는가
7. 해 보지 않은 것을 해 본 것처럼 쓴 곳이 없는가

`diagnose --profile blog`와 `structure`로 후보를 얻고 고친 뒤 `preserve`로 대조한다.

## Step 5. 발행 패키지

`../templates/publish-package.md`에 다음을 채운다.

| 항목 | 네이버 | 자체 블로그 |
|---|---|---|
| 제목(확정)과 후보 | ○ | ○ |
| 본문 | 평문 | Markdown |
| 메타 설명 | 해당 없음 | 80~150자(가정값), 글의 답을 한두 문장으로. "이 글에서는"으로 시작하지 않는다 |
| 주소 슬러그 | 해당 없음 | 핵심어 중심의 짧은 영문 또는 한글 |
| 태그 | 사용자가 원하는 수. 최대 30개로 알려져 있다(보고값) | 블로그의 기존 분류 안에서 |
| 카테고리 | 블로그의 기존 카테고리 가운데 하나 | 같음 |
| 사진 자리와 설명 | `[이미지: …]` 목록 | 대체 텍스트 문구 포함 |
| 내부 링크 | 관련 글 제목 | 링크 문구와 대상 |
| `[확인 필요]` | 발행 전 사람이 볼 것 | 같음 |

카테고리와 태그는 블로그에 이미 있는 것을 사용자에게 받아 그 안에서 고른다. 없는 분류를 새로 만들자고 할 때는 제안으로만 낸다.

검사:

```text
python ../scripts/korean_writing.py channel-check naver.txt --channel naver-blog --title "제목" --keyword "핵심어" --tags "태그1,태그2" --json
python ../scripts/korean_writing.py channel-check post.md --channel blog --title "제목" --keyword "핵심어" --meta "메타 설명" --json
```

| 코드 | 보는 것 |
|---|---|
| CH-3 | 네이버 평문에 남은 Markdown 기호 (`hold`) |
| CH-5·CH-6 | 문단 길이, 긴 문장 비율 |
| CH-7 | 제목 길이 |
| CH-8 | 핵심어가 제목·첫 문단에 있는지, 반복이 과한지 |
| CH-11 | 메타 설명 길이와 핵심어 |
| CH-12 | 소제목 수 |
| CH-13 | 대상을 알 수 없는 링크 문구 |
| CH-14 | 태그 수와 중복 |

## 시리즈

- 편마다 따로 읽혀도 질문 하나에 답해야 한다.
- 앞뒤 편 링크를 넣고 앞 편의 결론을 길게 되풀이하지 않는다.
- 용어와 수치가 편마다 같은지 `context-audit`로 대조한다.
