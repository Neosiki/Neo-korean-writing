# 채널 플레이북

채널마다 첫 화면에 보이는 양, 서식 지원, 읽는 상황이 다르다. 이 문서는 채널별 설계 기준과 발행 전 점검을 정리한다. 수치의 단일 원천은 `../scripts/channel_specs.json`이고 `channel-check`가 그 값을 읽는다.

## 수치의 근거 등급

| 등급 | 뜻 | 검사 결과 |
|---|---|---|
| `platform` | 플랫폼 공지나 여러 출처로 확인한 한도 | 넘으면 `hold` |
| `format` | 평문 채널에 남은 Markdown 기호처럼 화면에 그대로 드러나는 문제 | `hold` |
| `reported` | 2차 출처가 보고한 표시 기준. 기기에 따라 다르다 | `warn` |
| `assumption` | 운영 가정값. 플랫폼 한도가 아니다 | `warn` |
| `editorial` | 도입 유형 같은 편집 후보 | `warn` |

확인 기준일은 `channel_specs.json`의 `checked_on`이다. 플랫폼 정책은 바뀌므로 `platform` 값도 발행 시점에 다시 확인한다. 노출 알고리즘에 관한 통설은 사실로 쓰지 않는다. 필요하면 "운영 가설"로 표시하고 [성과 기록](performance-log.md)으로 검증한다.

`channel-check` 통과는 형식 점검 통과다. 반응이나 노출을 보증하지 않는다.

이 문서는 채널별 요약이다. 페이스북·블로그·브런치는 주제에서 발행본까지 가는 전용 절차가 있다.

| 채널 | 전용 절차 |
|---|---|
| 페이스북·카카오톡 평문 | [페이스북 글쓰기](channel-facebook.md) |
| 네이버 블로그, 자체 블로그·워드프레스 | [블로그 글쓰기](channel-blog.md) |
| 브런치스토리 | [브런치 글쓰기](channel-brunch.md) |

## 공통 설계

1. 접힘 전 첫 화면에서 글의 내용이 드러나야 한다. 첫 문장은 접힘 기준 안에서 끝낸다.
2. 도입과 마무리는 [도입과 마무리](opening-closing.md)의 유형에서 자료에 맞는 것을 고른다.
3. 해시태그·CTA·제목 후보는 사용자가 요구했거나 채널 계약에 있을 때만 만든다.
4. 수치·명칭·인용은 채널 변환 뒤에도 `preserve`로 대조한다.

## 페이스북·카카오톡 평문 (`facebook`)

- 서식: 평문. 굵게·소제목·표가 표시되지 않으므로 줄바꿈과 번호로 구조를 만든다.
- 첫 화면: 접힘 기준 120자(가정값). 첫 두세 문장에 글의 방향이 보이게 쓴다.
- 분량: 2,000자 이내(가정값). 프롬프트·템플릿 같은 실물을 붙일 때는 넘을 수 있다.
- 문단: 200자 이내(가정값)로 끊고 문단 사이를 한 줄 띄운다.
- 글의 쓰임에 따라 구조를 고른다.

| 쓰임 | 구조 |
|---|---|
| 관점 제시 | 관찰 → 문제 다시 보기 → 내 작업·근거 → 판단 |
| 경험 공유 | 기존 방식 → 바꾼 점 → 달라진 결과 → 남은 한계 |
| 방법 안내 | 무엇을 얻는지 → 순서별 설명 → 바로 쓸 예시 |
| 자료 배포 | 배경 짧게 → 구분선 → 실물 전문 |
| 점검 기준 | 흔한 증상 → 원인 → 번호 매긴 점검 항목 → 다음 행동 |

경험·작업 과정·결과 수치는 제공된 자료에 있을 때만 쓴다.

## 네이버 블로그 정보글 (`naver-blog`)

- 한 글은 하나의 검색 의도에 답한다. 여러 주제를 한 글에 섞지 않는다.
- 핵심어는 사용자가 정한다. 후보가 필요하면 제안하되 검색량·경쟁도를 지어내지 않는다.
- 제목: 15~35자(가정값), 핵심어를 앞쪽에 둔다. 본문이 주지 않는 정보를 제목이 약속하지 않는다.
- 도입: 첫 문단에서 독자가 찾던 답의 범위를 밝힌다.
- 본문: 평문. 문단 150자 이내(가정값), 60자를 넘는 문장이 30%를 넘지 않게(가정값) 끊는다.
- 핵심어는 문맥에 맞을 때만 넣는다. 1,000자당 8회(가정값)를 넘으면 `channel-check`가 기계적 반복 후보로 올린다.
- 사진 자리는 `[이미지: 설명]`으로 표시한다. 찍지 않은 사진의 내용을 본문에서 묘사하지 않는다.
- 직접 가 보거나 써 본 내용은 사용자가 제공한 경우에만 쓴다. 체험이 없는 글을 체험 후기처럼 쓰지 않는다.

| 글 종류 | 구조 |
|---|---|
| 방법·순서 | 준비물·조건 → 단계별 설명 → 자주 막히는 지점 → 정리 |
| 비교·선택 | 선택 기준 → 항목별 비교 → 상황별 권고 |
| 후기·체험 | 이용 조건(일시·비용·제공 여부) → 겪은 순서 → 좋았던 점·아쉬운 점 → 맞는 사람 |

협찬·제공을 받은 글은 그 사실을 글 앞쪽에 밝힌다.

## 자체 블로그·워드프레스 (`blog`)

- 서식: Markdown 소제목·목록·링크.
- 제목 50자 이내, 메타 설명 80~150자, 문단 400자 이내(모두 가정값).
- 1,500자 이상이면 `##` 소제목 2~6개(가정값). 소제목만 읽어도 순서가 보이게 쓴다.
- 링크 문구는 대상의 제목이나 이름으로 쓴다.

## 스레드 (`threads`)

- 포스트 하나는 500자(플랫폼 한도). 초안에서는 `---` 한 줄로 포스트를 나눈다.
- 기본 구성은 3포스트(사용자 기본값). 긴 글은 세 포스트로 압축한다.
- 각 포스트는 따로 읽혀도 뜻이 통해야 한다. "앞에서 말했듯" 같은 의존 표현을 줄인다.
- 포스트 역할 예: ① 판단이나 장면 ② 근거·과정 ③ 적용 범위나 남은 질문.
- 500자를 넘는 한 편이 필요하면 텍스트 첨부(10,000자, 플랫폼 한도)를 쓸지 사용자에게 묻는다.
- 문체는 반말 「어」체다(~했어, ~같아, ~거든, ~더라, ~보려고 해). 합니다체(~합니다, ~습니다)와 ~이다체를 섞지 않는다. 합니다체는 페이스북·카카오톡용이다.
- 사용자가 문장 수를 정하면(예: 두 문장) 그 수를 지킨다. 매장 이름·업종·대표 이름처럼 누구인지 알아볼 수 있는 정보는 쓰지 않는다.

## 인스타그램 캡션 (`instagram`)

- 캡션 2,200자, 해시태그 30개(플랫폼 한도). 접힘 기준은 약 125자(보고값).
- 사진·영상이 본체다. 캡션은 화면에 없는 정보(조건·가격·위치·기간)를 보탠다.
- 해시태그는 사용자가 요청한 수만 만든다.

## 브런치스토리 (`brunch`)

- 서식: 소제목·구분선·인용을 쓸 수 있다. 짧은 글에 소제목을 과하게 넣지 않는다.
- 제목 30자 이내, 본문 3,000자 안팎(둘 다 가정값). 핵심 낱말을 제목 앞쪽에 둔다.
- 검색보다 추천으로 읽히는 채널이므로 도입에서 글의 관점이 보여야 한다.
- 에세이라면 [에세이 시선 점검](essay-gaze.md)을 함께 쓴다.

## 뉴스레터 (`newsletter`)

- 제목 40자 이내, 본문 1,500자 안팎(가정값). 한 호에 주제는 한두 가지.
- 링크·날짜·신청 방법은 LOCK으로 잡고 발송 전 다시 대조한다.

## 발행 전 검사

```text
python ../scripts/korean_writing.py channel-check final.txt --channel threads
python ../scripts/korean_writing.py channel-check final.txt --channel naver-blog --title "제목" --keyword "핵심어" --json
python ../scripts/korean_writing.py channel-check post.md --channel blog --title "제목" --keyword "핵심어" --meta "메타 설명" --json
python ../scripts/korean_writing.py channel-check brunch.md --channel brunch --title "제목" --tags "키워드1,키워드2" --json
```

`hold`가 있으면 고친 뒤 발행본으로 낸다. `warn`은 유지 조건을 보고 판단하며 유지한 항목은 사용자에게 알린다. `--strict`는 `warn`도 종료 코드 1로 돌려준다.
