# 사업계획서 작성

정부지원사업·공모전·기관 제출용 사업계획서를 쓰는 절차다. 예비창업패키지·초기창업패키지처럼 문제인식·실현가능성·성장전략·팀 구성(PSST)으로 짜인 양식을 기본으로 하되, 다른 양식에도 같은 순서로 적용한다.

사업계획서는 신청자의 사업을 신청자의 근거로 설명하는 문서다. 이 절차에서 에이전트의 일은 신청자가 가진 사실을 양식에 맞게 정리하고 빈 곳을 찾아 주는 것이다. 실적·경력·특허·매출·고객 반응을 지어내지 않는다.

## 세 가지 원칙

1. **양식이 먼저다.** 항목 이름, 순서, 분량, 표 형식, 글자 크기, 제출 파일 형식은 그해 공고문과 양식 파일이 정한다. 이 문서의 PSST 기본 골격은 양식을 받기 전의 출발점일 뿐이다. 양식과 다르면 양식을 따른다.
2. **근거는 주인이 있다.** 수치와 사실마다 누구의 것인지(시장 통계 / 남의 사례 / 신청자 자신)와 출처를 붙인다. 남의 사례에서 본 기능·성과·자금 규모를 신청자의 계획이나 실적으로 옮겨 쓰지 않는다.
3. **빈칸은 빈칸으로 둔다.** 확인하지 못한 값은 `[확인 필요]`, 신청자만 아는 값은 `[입력 필요: 항목]`으로 표시한다. 업종 평균이나 예시로 대신 채우지 않는다. 자리표시자가 남은 원고는 제출본이 아니다.

## 전체 순서

```text
Step 1. 공고·양식 확인 → 양식 목차 확정
Step 2. 근거 카드 5종 (시장·문제 / 유사 사례 / 자금·지원 / 경쟁 / 신청자 정보)
Step 3. 항목별 주장–근거 설계
Step 4. 본문 작성
Step 5. 검수 (기계 점검 + 평가자 관점 읽기)
Step 6. 제출 준비, 필요하면 발표 자료
```

근거 카드는 [근거 카드](bizplan-evidence.md), 발표 자료는 [발표 원고와 슬라이드 문안](bizplan-pitch.md)을 따른다.

들어오는 상태에 따라 시작점이 다르다.

| 가진 것 | 시작 |
|---|---|
| 아이템만 있음 | Step 1 |
| 양식과 메모가 있음 | Step 2, 신청자 정보 카드부터 |
| 근거 자료가 정리돼 있음 | Step 3 |
| 써 둔 초안이 있음 | Step 5의 점검부터 하고 빈 곳을 Step 2로 되돌린다 |
| 다른 공고에 낸 계획서가 있음 | Step 1에서 새 양식과 항목을 대응시키고 달라진 항목만 다시 쓴다 |

## Step 1. 공고·양식 확인

사용자에게 공고문과 양식 파일을 받는다. 없으면 받을 수 있는지 먼저 묻는다.

확인할 것:

- 사업명, 주관기관, 접수 마감, 신청 자격
- 양식의 항목 이름과 순서, 쪽수·글자 수 제한, 표·그림 허용 범위
- 평가 항목과 배점, 가점·감점 사항
- 사업비 구성 규칙: 정부지원금과 자기부담 비율, 쓸 수 있는 비목
- 제출 파일 형식과 삭제해야 하는 안내 문구

공고문에 없는 평가 기준이나 "합격하는 요령"을 사실처럼 쓰지 않는다. 자격·마감·사업비 규칙처럼 틀리면 탈락이나 환수로 이어지는 항목은 공고문 문장을 근거로 적고 사용자에게 다시 확인받는다.

양식 목차를 `../templates/bizplan-outline.json` 형식으로 옮겨 둔다. 이 파일이 있으면 `bizplan-check`가 항목 누락과 항목별 분량을 양식 기준으로 본다.

양식을 받지 못했을 때의 기본 골격:

| 영역 | 평가자가 알고 싶은 것 |
|---|---|
| 일반현황·개요(요약) | 한눈에 무슨 사업인가 |
| 문제인식 | 누가 어떤 문제를 겪고, 그것이 왜 지금 풀 만한가 |
| 실현가능성 | 무엇을 만들고 어디까지 준비됐고, 남과 무엇이 다른가 |
| 성장전략 | 어떻게 팔고, 돈을 어떻게 쓰고 마련하며, 언제 무엇을 하는가 |
| 팀 구성 | 이 사람들이 이 일을 해낼 수 있는가 |

세부 항목 이름은 해마다 달라진다. 기본 골격으로 쓴 초안은 양식을 받은 뒤 항목을 다시 대응시킨다.

## Step 2. 근거 카드

[근거 카드](bizplan-evidence.md)의 5종을 만든다. 조사로 채우는 카드(시장·문제, 유사 사례, 자금·지원, 경쟁)와 신청자만 채울 수 있는 카드(신청자 정보)를 나눈다. 신청자 정보 질문지를 먼저 건네고 조사는 그동안 진행한다.

## Step 3. 항목별 주장–근거 설계

본문을 쓰기 전에 양식 항목마다 다음 한 줄을 적는다.

```text
[항목] 이 항목에서 평가자가 얻어야 할 답 한 문장 ← 근거 카드의 어느 줄 / 넣을 표·그림
```

- 답 한 문장이 써지지 않는 항목은 근거가 모자란 항목이다. 본문으로 넘기지 말고 Step 2로 돌아간다.
- 같은 근거를 여러 항목에서 되풀이하지 않는다. 한 곳에서 자세히 쓰고 다른 곳은 가리킨다.
- 항목끼리 숫자가 이어지는지 본다: 목표 고객 수 → 목표 매출 → 자금 소요 → 일정 → 인력.

이 설계가 Writer–Editor 인계 계약의 `provenance`가 된다. 근거 카드의 줄은 `sourced_claims`, 신청자의 판단은 `author_interpretations`, 빈칸은 `unresolved`에 넣는다.

## Step 4. 본문 작성

서술체:

- 양식이나 사용자가 정하지 않았으면 개조식(~함, ~임)으로 쓴다. 한 문서 안에서 섞지 않는다.
- 한 줄에 사실 하나. 주어와 행위자를 살린다. "추진될 예정임"보다 "대표자가 3월까지 시제품을 제작함".
- 수치에는 단위·기준 시점·출처를 붙인다. 금액은 양식의 단위(원, 천원, 백만원)를 따른다.
- 계획과 실적을 구분한다. 한 일은 과거형으로, 할 일은 시기와 함께 쓴다.
- 가능성·추정은 그대로 둔다. "전망됨", "추정됨"을 "됨"으로 바꾸면 사실이 달라진다.
- 최상급과 평가어("국내 최초", "유일", "압도적")는 근거가 있을 때만 쓰고 근거를 바로 뒤에 적는다.

영역별로 쓸 내용과 흔한 결함:

| 영역 | 쓸 내용 | 흔한 결함 |
|---|---|---|
| 개요(요약) | 아이템 한 문장, 대상 고객, 핵심 근거 수치 한두 개, 요청 사항 | 본문에 없는 내용이 요약에만 있음 |
| 문제인식 | 누가, 어떤 상황에서, 얼마나 자주·크게 겪는가. 지금 쓰는 대안과 그 한계. 시장 규모와 산정 방식 | 문제 대신 해결책 소개로 시작함. 시장 전체 규모만 있고 내가 닿을 범위가 없음 |
| 실현가능성 | 만들 것의 범위, 현재 준비 정도와 증빙, 개발·제작 단계, 경쟁·대체재와 같은 기준의 비교 | 준비 정도를 형용사로만 씀. 비교 기준이 나에게만 유리함 |
| 성장전략 | 첫 고객을 만나는 경로, 가격과 수익 구조, 사업비 용도와 산출 근거, 자금 조달, 월별 일정 | 매출 목표의 산식이 없음. 사업비 합계가 맞지 않음. 일정과 인력이 따로 놂 |
| 팀 구성 | 대표자와 팀원이 이 사업에서 맡는 일과 그 일을 뒷받침하는 경력, 모자란 역량과 메울 방법, 협력처 | 이력 나열에 그침. 협력처가 확정인지 협의 중인지 구분이 없음 |

시장 규모(TAM·SAM·SOM)를 쓸 때:

- 세 값의 정의와 산식을 표 아래에 적는다. 값만 있고 산식이 없으면 평가자가 검증할 수 없다.
- TAM은 공공 통계나 출처가 분명한 조사에서 가져온다. SAM·SOM은 신청자의 가정이므로 가정임을 밝힌다.
- 순서는 TAM ≥ SAM ≥ SOM이다. 연도와 단위를 맞춘다.

사업비 표를 쓸 때:

- 비목 이름과 한도는 공고의 사업비 기준을 따른다.
- 줄마다 산출 근거(단가 × 수량 × 기간)를 적는다. 견적을 받지 않은 값은 추정임을 밝힌다.
- 합계와 비율을 계산으로 확인한다. `bizplan-check`가 합계 불일치를 `hold`로 잡는다.

표와 그림:

- 표는 비교·금액·일정처럼 나란히 놓아야 읽히는 내용에 쓴다. 표 아래에 출처나 "자체 작성"을 적는다.
- 그림 자리는 `[그림: 무엇을 보여 주는지]`로 표시한다. 없는 화면·시제품 사진을 있는 것처럼 설명하지 않는다.

## Step 5. 검수

기계 점검:

```text
python ../scripts/korean_writing.py bizplan-check 사업계획서.md --outline 양식목차.json --json
python ../scripts/korean_writing.py diagnose 사업계획서.md --profile official --json
python ../scripts/korean_writing.py preserve 이전본.md 수정본.md --strict --json
```

| 코드 | 보는 것 | 결과 |
|---|---|---|
| BP-1 | `[확인 필요]`, `[입력 필요]`, `{ }`, ○○ 같은 자리표시자 | `hold` |
| BP-2 | 양식 항목 누락·빈 항목 (`--outline`이 있을 때). 없으면 PSST 기본 영역 유무 | `hold` / `warn` |
| BP-3 | 시장·통계 수치가 있는데 출처 표기가 없는 문단 | `warn` |
| BP-4 | 표의 항목 합과 합계 행 불일치 | `hold` |
| BP-5 | 개조식과 합니다체 혼용 | `warn` |
| BP-6 | 양식 목차에 적은 항목별 분량 초과 | `warn` |
| BP-9 | TAM ≥ SAM ≥ SOM 순서 위반 | `hold` |

기계 점검은 형식·산술·표기만 본다. 사업성, 수치가 사실인지, 선정 가능성은 판정하지 않는다. 통과를 "잘 쓴 계획서"라는 뜻으로 보고하지 않는다.

평가자 관점 읽기(사람과 에이전트가 함께):

1. 개요만 읽고 무슨 사업인지, 무엇을 요청하는지 아는가
2. 문제의 크기가 숫자와 사례로 보이는가. 그 숫자의 출처가 있는가
3. "어디까지 됐는가"에 증빙(시제품, 테스트 기록, 계약, 등록번호)이 붙어 있는가
4. 경쟁 비교의 기준이 고객 입장에서 중요한 기준인가
5. 매출 목표의 산식을 따라 계산하면 같은 값이 나오는가
6. 사업비 → 일정 → 인력이 서로 맞는가. 3월에 뽑는다는 사람이 2월 일정에 나오지 않는가
7. 팀의 경력이 맡은 일과 이어지는가
8. 공고의 평가 항목마다 답하는 자리가 본문에 있는가

찾은 문제는 고칠 수 있는 것(문장·표기·산술)과 신청자가 정해야 하는 것(목표, 가정, 사실 확인)으로 나눠 보고한다. 뒤쪽은 에이전트가 정하지 않는다.

## Step 6. 제출 준비

- 자리표시자 0건, 표 합계 일치, 양식의 안내 문구 삭제 여부를 마지막으로 확인한다.
- 개인정보·가점 서류·증빙 목록은 공고문의 제출 서류 목록과 대조한다.
- 파일 변환(.docx, .hwpx, .pdf)은 이 스킬의 범위 밖이다. 환경에 문서 도구가 있으면 그 도구로 만들고 변환 뒤 표·쪽수·글자 크기가 양식과 같은지 사용자가 확인한다.
- 제출 전 최종 확인과 제출은 신청자가 한다. 사업계획서의 내용에 대한 책임은 신청자에게 있다.

## 다른 공고에 다시 낼 때

1. 새 양식의 목차를 받아 기존 항목과 대응표를 만든다. 대응하는 항목이 없는 곳이 새로 쓸 곳이다.
2. 근거 카드는 다시 쓴다. 다만 통계의 기준 연도, 지원사업 일정, 경쟁사 현황은 새로 확인한다.
3. 분량 제한이 다르면 [원소스 변환](repurposing.md)의 "줄이는 변환" 기록을 남긴다. 조건·한계가 빠져 단정이 세지지 않게 한다.
4. 같은 내용을 두 공고에 내도 되는지(중복 지원·동시 수행 제한)는 공고문에서 확인하고 사용자에게 알린다.
